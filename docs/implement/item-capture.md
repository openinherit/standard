# Item Capture

## Introduction

Adding items is the highest-frequency activity in any INHERIT-backed application. It is also the activity where user behaviour varies most. Unlike a marketplace listing flow, where a seller lists one item at a time with commercial intent, people cataloguing what they own tend to add **many items in one sitting**, and they arrive with very different amounts of patience and information.

Three capture behaviours recur:

| Mode | User behaviour | What they have at capture time |
|------|----------------|--------------------------------|
| **A — Photo-first** | Takes a photo, moves on, intends to return later | An image and nothing else |
| **B — Bulk** | Walks a room adding many items quickly | A name and rough category per item |
| **C — Detailed** | Documents one item thoroughly, including its room | Name, category, room, condition, identifiers, value |

An interface must serve all three without forking the data model. This guide shows how each maps onto the same `asset.json` entity, which fields carry the "come back to this later" signal, and where the current schema constrains what an interface can do.

Every JSON fragment in this guide is annotated with the schema it must satisfy, and validated against the v6.6 schemas as published. **No fragment uses an extension** — everything below is in the open core.

---

## The one hard constraint

`asset.json` requires exactly three fields:

```json
"required": [ "id", "name", "category" ]
```

`id` is generated by the application, so in practice the user must supply **a name and a category** before an item can exist as a conformant `Asset`. This single fact shapes every capture flow below. In particular, a photo-only item **cannot** be represented as a valid `Asset`:

<!-- validate: v3/asset.json expect-invalid -->
```json
{
  "id": "1c9e6f2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
  "images": [
    { "url": "https://cdn.example.com/capture/IMG_4471.jpg", "mediaType": "image/jpeg" }
  ]
}
```

This fails validation with `must have required property 'name'` and `must have required property 'category'`. Mode A therefore needs an explicit strategy, described next.

---

## Mode A — Photo-first capture

The user photographs something and defers everything else. Two strategies are conformant. Choose one and apply it consistently, because they differ in what other tools can see.

### Strategy A1 — Hold drafts outside the document (recommended default)

Keep unresolved captures in application-local storage. Promote a capture into the INHERIT document only once it has a name and a category, whether supplied by the user or by a vision model the user has accepted.

**Why prefer this:** an INHERIT document stays a set of assertions the owner stands behind. Unresolved photos are not yet assertions. Exports, valuations, completeness scores, and dealer-facing views never have to special-case placeholder rows.

**Cost:** unresolved captures do not travel between tools. If the user switches application, their photo backlog stays behind.

### Strategy A2 — Emit a valid placeholder Asset

When the backlog itself must be portable — a shared household catalogue, or a device-to-server sync that carries no private side channel — emit a schema-valid `Asset` that is explicitly marked as unresolved:

<!-- validate: v3/asset.json -->
```json
{
  "id": "1c9e6f2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
  "name": "Unidentified item — photographed 2026-08-17",
  "category": "other",
  "images": [
    {
      "url": "https://cdn.example.com/capture/IMG_4471.jpg",
      "mediaType": "image/jpeg",
      "viewType": "overview",
      "takenAt": "2026-08-17T09:14:00Z"
    }
  ],
  "dataProvenance": "manual_entry",
  "condition": "unknown",
  "valuationConfidence": "unknown",
  "provenance": { "source": "manual", "confidence": 0, "humanVerdict": "pending_review" }
}
```

Five things carry the signal, and each is doing a distinct job:

- **`category: "other"`** satisfies the requirement. Note the semantic cost: `other` properly means "a real category outside the enum", so a placeholder is indistinguishable from a genuine `other` on the asset alone. The document-level marker below is what disambiguates it.
- **`dataProvenance: "manual_entry"`** records how the data got here. It is a per-entity override of the document-level default, and its values are `manual_entry | ai_extracted | ocr_scanned | imported | migrated | system_generated`.
- **`provenance.confidence: 0`** is the schema's own "no confidence" end of the 0.0–1.0 scale.
- **`provenance.humanVerdict: "pending_review"`** is the nearest core field to "needs attention". Read its definition carefully — it is a *human review verdict on AI-generated or imported data*. Using it for a manually captured draft stretches it. It is the best per-asset signal today, not a precise one.
- **No `lastVerifiedAt` and no `verifiedBy`.** Their *absence* is the honest statement that nobody has yet stood behind this row. Do not populate them at capture time to make a form feel finished.

#### The unambiguous marker lives at document level

The asset alone cannot say "the owner has not finished with this". The document can, in two places that already exist, and both are open core:

<!-- validate: v3/catalogue.json -->
```json
{
  "$schema": "https://openinherit.org/v3/catalogue.json",
  "schemaVersion": "6.6.0",
  "assets": [
    {
      "id": "1c9e6f2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
      "name": "Unidentified item — photographed 2026-08-17",
      "category": "other",
      "dataProvenance": "manual_entry",
      "provenance": { "source": "manual", "confidence": 0, "humanVerdict": "pending_review" }
    }
  ],
  "completeness": {
    "score": 38,
    "maxScore": 100,
    "calculatedAt": "2026-08-17T09:20:00Z",
    "checklist": [
      {
        "category": "assets_and_valuations",
        "item": "Captured items have a name and a category",
        "weight": 5,
        "status": "incomplete",
        "details": "12 items captured from photographs are not yet named or categorised"
      }
    ]
  },
  "recommendedActions": [
    {
      "id": "act-capture-001",
      "category": "completeness",
      "priority": "medium",
      "title": "Identify 12 items photographed in the loft",
      "description": "These items were photographed but not named. Naming and categorising them makes them count towards estate totals.",
      "status": "pending",
      "triggeredBy": "12 assets have category 'other' and humanVerdict 'pending_review'",
      "relatedEntityType": "asset",
      "relatedEntityId": "1c9e6f2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b"
    }
  ]
}
```

- **`completeness`** (`common/completeness.json`, referenced by both `catalogue.json` and `schema.json`) is the canonical answer to *"what is still missing in this document"*. `checklist[]` items require `category`, `item`, `weight` and `status`, and forbid any other key. The `category` enum has no capture-specific value; **`assets_and_valuations` is the one to use**, with the specifics in `details`.
- **`recommendedActions[]`** (`schema.json#/$defs/RecommendedAction`) is the per-item marker. `relatedEntityType: "asset"` plus `relatedEntityId` names the exact placeholder, `category: "completeness"` says why, `triggeredBy` records the rule that raised it, and `status` gives it a lifecycle — `pending`, then `completed` when the user names the item or `dismissed` when they decide not to. Required fields are `id`, `category`, `priority`, `title` and `status`.

⚠️ **Scope matters and is easy to get wrong.** `Completeness` is **document-scoped** — it is not a property of `asset.json`. Per-asset "how did this data get here and has anyone checked it" is `dataProvenance` / `provenance` / `fieldProvenance` / `suggestedSubcategory`. Per-document "what is still missing, and which rows need work" is `completeness` and `recommendedActions`. Reaching for the wrong scope is how implementations end up wanting a new field.

**Interfaces using A2 must exclude unresolved placeholders from value totals, completeness scores, and any dealer- or executor-facing view.** A placeholder counted as an asset is worse than no asset. The `recommendedActions` row is the machine-readable list of what to exclude.

### Returning to the backlog

Both strategies need a resurfacing mechanism, and it is the same `recommendedActions` array. Putting "you have 12 unidentified photos from the loft" there rather than in an interface-only notification means the prompt survives a reinstall and travels with the document.

## Mode B — Bulk capture

Bulk capture is the common case and deserves the fastest path: name, category, and nothing else. That validates:

<!-- validate: v3/asset.json -->
```json
{
  "id": "2c9e6f2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
  "name": "Ercol dining chair",
  "category": "property_contents",
  "quantity": 6,
  "spaceId": "3c9e6f2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b"
}
```

### Choosing the right grouping construct

Four fields group items, and conflating them causes lasting data problems. They are not interchangeable:

| Construct | Means | Use when |
|-----------|-------|----------|
| `quantity` | *n* interchangeable instances of one item | Six identical dining chairs, 500 identical bricks |
| `spaceId` | Physically located in the same place | Everything captured while standing in the loft |
| `containedInAssetId` | Physically inside another asset | Watches in a safe, tools in a toolbox |
| `assetCollectionId` | Owner-curated set that should be valued and sold together | A model railway collection, a vinyl library |

**Do not use `assetCollectionId` for capture batches.** An `AssetCollection` carries `disposalStrategy`, `minimumAcceptableValue`, `preferredDisposalMethod`, and `specialistDealerNotes` — it asserts that these items belong together commercially. "I added these twelve things on Sunday afternoon" is not that claim. A dealer reading the document would be misled.

`quantity` also has a limit worth designing around: it collapses items into one row, so per-item condition, images, and identifiers are lost. Six chairs where one is damaged are two assets — `quantity: 5` and `quantity: 1` — not one row of six.

### Batch identity

⭐ **The core schema does have a batch-identity mechanism.** `provenance.importSourceId` is on every entity that carries `provenance` — assets included — and its definition is *"References `importSources[].id` on the root document"*. The root document side is `importSources[]`, an array of `ImportSource` (`id` and `systemName` required; `importDate`, `importMethod`, `notes` optional), and `importMethod` includes `manual_copy` and `ai_extraction` alongside `api` and `file_upload`.

So a batch is expressed like this, with no extension and no new field:

<!-- validate: v3/catalogue.json -->
```json
{
  "$schema": "https://openinherit.org/v3/catalogue.json",
  "assets": [
    {
      "id": "2c9e6f2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
      "name": "Ercol dining chair",
      "category": "property_contents",
      "quantity": 6,
      "provenance": { "source": "manual", "importSourceId": "cap-2026-08-17-loft" }
    }
  ],
  "importSources": [
    {
      "id": "cap-2026-08-17-loft",
      "systemName": "LegacyLists",
      "importDate": "2026-08-17",
      "importMethod": "manual_copy",
      "notes": "Walk-the-room capture session, loft, 14 items"
    }
  ]
}
```

That gives an interface everything batch identity was wanted for — undo the batch, show progress across it, and offer "finish what you started on Sunday" — by selecting on `provenance.importSourceId`.

⚠️ **One honest mismatch, and it is not this guide's to settle.** `ImportSource` means *the system the data came from*, and `systemName` is required. A purely in-app manual capture session is not an import from anywhere, so `systemName` ends up naming the capturing application, and `importDate` ends up meaning "captured on". That stretches the entity, in the same way `humanVerdict` stretches for a hand-typed draft. **Batch identity belongs to the catalogue item-import adapter**, which is a separate piece of work with its own proposal — the residual question of whether manual capture sessions get first-class batch semantics belongs there, not here. Do not mint a new extension key for it in the meantime.

### One photo, several items

A single photo of a shelf often yields many items. `images` is per-asset and `media.json` has no region or bounding-box field — its properties are exactly `caption`, `content`, `mediaType`, `takenAt`, `thumbnailUrl`, `url` and `viewType` — so the same `url` is repeated on each asset created from that photo. Set `viewType: "overview"` on the shared shot and give each asset its own close-up where one exists. Tools can group by identical `url` if they need to reconstruct the source frame; do not rely on that for anything load-bearing.

## Mode C — Detailed capture

Detailed capture is well served. All of this validates on a single asset:

<!-- validate: v3/asset.json -->
```json
{
  "id": "4c9e6f2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
  "name": "Omega Speedmaster Professional 3570.50",
  "category": "jewellery_watches",
  "subcategory": "wristwatch",
  "brand": "Omega",
  "model": "Speedmaster Professional 3570.50",
  "spaceId": "5c9e6f2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
  "spaceIdDisplay": "Safe, study, first floor",
  "containedInAssetId": "6c9e6f2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
  "assetCollectionId": "7c9e6f2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
  "condition": "excellent",
  "originalPackaging": "complete",
  "estimatedValue": { "amount": 420000, "currency": "GBP" },
  "valuationConfidence": "estimated",
  "identifiers": [ { "type": "serial_number", "value": "84512299" } ],
  "lastVerifiedAt": "2026-08-17T09:14:00Z",
  "verifiedBy": "owner"
}
```

Watch the enum values, which are easy to guess wrong:

- `valuationConfidence` is `estimated | professional | official | unknown` — **`estimated`, not `estimate`**.
- `originalPackaging` is `complete | partial | box_only | papers_only | none | unknown`.
- `condition` is `excellent | good | fair | poor | unknown | not_applicable`. Use `not_applicable` for financial assets.
- ⚠️ **`provenance.source` and `dataProvenance` are different vocabularies and are easy to cross.** `provenance.source` is `import | manual | ai_generated`. `dataProvenance` is `manual_entry | ai_extracted | ocr_scanned | imported | migrated | system_generated`. Strategy A2 above uses both fields in one asset, so the mistake is one keystroke away: `"source": "manual_entry"` is invalid, and `"dataProvenance": "manual"` is invalid.
- `spaceId` is nullable (`["string", "null"]`), so an explicit "room not recorded" is expressible without omitting the key.

### Driving the form from reference data

Do not hard-code per-category form fields. `reference-data/category-guidance.json` supplies, per category, eleven keys: `label`, `description`, `financial`, `subcategories`, `recommendedIdentifiers`, `recommendedViewTypes`, `recommendedBrands`, `defaultUrgency`, `containerFlag`, `locationClass`, and `typicalValuationMethod`. An interface that reads this file asks for a serial number on a watch and a sort code on a bank account without a single conditional in the view layer, offers the right camera prompts from `recommendedViewTypes`, and stays correct as the taxonomy grows.

Similarly, `reference-data/space-types.json` carries display metadata for every `spaceType` in `space.json`, so the room picker is generated rather than maintained.

### Recording which room

Rooms are a first-class entity. `space.json` covers 101 space types, including off-site locations (`self_storage`, `safe_deposit_box`, `workplace`), portable items that travel with the owner (`portable`), and culturally specific rooms (`puja_room`, `majlis`, `genkan`, `tatami_room`). It also carries `floor`, a personalising `name` ("Dad's workshop"), access `notes`, and its own `images`.

Assets reference a room through `spaceId`, with `spaceIdDisplay` available as a denormalised label so list views need no join.

> **Known gap — rooms in catalogue documents.** `space.json` requires `propertyId` (its required set is `id`, `propertyId`, `spaceType`), but `catalogue.json` has a `spaces` array and **no `properties` array**. A catalogue-only document — precisely the living-collector flow this guide is about — therefore cannot record a room without pointing `propertyId` at a UUID that does not exist in the document.
>
> Two measurements make this a defect rather than an opinion. First, the shipped referential-integrity rules check `assets[].propertyId` and carry **no** rule for `spaces[].propertyId`, so such a document passes every shipped check with a dangling reference in it. Second, the shipped `examples/fixtures/catalogue-only.json` has no `spaces` key at all, so the gap is unexercised rather than resolved.
>
> Until it is addressed, an interface building catalogue documents must either omit `spaces` and put the room in the asset's free-text `location`, or mint a stable synthetic property UUID per address and accept that the reference dangles. **This gap is tracked as a defect in its own right** — it is not something an implementer should work around silently, and it is not something to paper over with an extension. See *Open questions* below.

## Progressive enrichment

The three modes are not three kinds of item. They are three entry points to one entity, and most real items move between them: photographed on Sunday, named on Monday, valued when a dealer visits. The schema is built for this, and the fields that make it work are easy to overlook.

| Field | Job |
|-------|-----|
| `dataProvenance` | Per-asset record of how this entity's data was captured, overriding the document default |
| `fieldProvenance[]` | Per-field record of how each value was obtained, with `confidence` 0–100. `field`, `method` and `extractedAt` are **all required** on every entry |
| `suggestedSubcategory` | AI's suggestion, kept **separate** from the human-set `subcategory` |
| `provenance.humanVerdict` | `approved`, `rejected`, `modified`, `pending_review` — with `verdictAt` and `rejectionReason` alongside |
| `provenance.aiProvenance` | Which model produced the data, and its own 0–100 confidence |
| `lastVerifiedAt` / `verifiedBy` | When a human last stood behind this data |
| `valuationReliability` | 0–100 score derived from valuation recency and method |

A vision model's guess and the owner's confirmation are different claims, and the schema keeps them apart. An enrichment pass writes into `suggestedSubcategory` and `fieldProvenance`; it does not overwrite what the owner typed. This validates:

<!-- validate: v3/asset.json -->
```json
{
  "id": "8c9e6f2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
  "name": "Hornby R3456 Class 66 EWS Locomotive",
  "category": "collectibles",
  "suggestedSubcategory": "model_railways",
  "provenance": { "source": "ai_generated", "confidence": 0.72, "humanVerdict": "pending_review" },
  "fieldProvenance": [
    { "field": "name", "method": "ai_extracted", "confidence": 72, "extractedAt": "2026-08-17T09:14:02Z" }
  ]
}
```

Note the two confidence scales: `provenance.confidence` is a number 0.0–1.0, while `fieldProvenance[].confidence` is an integer 0–100. `fieldProvenance[].method` is `manual_entry | ai_extracted | imported | computed | ocr_scanned`.

## Validation checklist

Before shipping a capture flow, confirm:

1. ☐ An item with only `id`, `name`, `category` round-trips and validates.
2. ☐ Unresolved captures each carry a `recommendedActions` row naming them by `relatedEntityId`, and are excluded from value totals and completeness scores.
3. ☐ The document's `completeness.checklist[]` records outstanding capture work under `assets_and_valuations`, rather than an interface-only counter.
4. ☐ `assetCollectionId` is never written for a capture batch. Batches use `provenance.importSourceId` → `importSources[]`.
5. ☐ Per-category fields come from `reference-data/category-guidance.json`, not hard-coded.
6. ☐ Room pickers come from `reference-data/space-types.json`.
7. ☐ AI suggestions land in `suggestedSubcategory` / `fieldProvenance`, never overwriting owner-entered values.
8. ☐ `lastVerifiedAt` / `verifiedBy` are written only when a human actually verified something.
9. ☐ Enum values match exactly — `estimated`, not `estimate`; `provenance.source` values are not `dataProvenance` values.
10. ☐ No `x-inherit-*` key is being used to carry capture state. Everything in this guide is open core.
11. ☐ If building catalogue documents, the `spaces` / `propertyId` gap above is handled deliberately.

## Open questions for the standard

These are recorded here because they affect capture interfaces directly. None is decided, and none should be treated as a commitment.

1. **Rooms in catalogue documents.** Either relax `space.json`'s `propertyId` requirement, or add a `properties` array to `catalogue.json`. Relaxing the requirement is backwards-compatible; adding the array is additive. Both are narrow. Either would let catalogue users record which room an item is in, which is a core expectation of the flow. A third, smaller change is worth considering alongside them: add the missing referential-integrity rule for `spaces[].propertyId`, so that whichever route is chosen, a dangling room reference stops passing validation silently.
2. **Per-asset capture state.** The *document* level is covered — `completeness` says what is missing and `recommendedActions` says which rows need work. What is genuinely absent is a field **on the asset** meaning "the owner has not finished with this". `provenance.humanVerdict: pending_review` is being borrowed for a job it was not defined for, and the honest per-asset signal today is a combination: `dataProvenance: manual_entry`, `provenance.confidence: 0`, and `lastVerifiedAt` left absent. A dedicated per-asset field would make that a single readable fact instead of an inference.
3. **Unknown versus other.** `category` is required and has no "not yet determined" value, so unresolved items are filed as `other` and become indistinguishable from genuine `other` items on the asset alone. Today the `recommendedActions` row is what tells them apart.
4. **Media regions.** `media.json` has no region field, so one photo depicting many items must be duplicated across every asset derived from it.
5. **Manual capture sessions as batches.** `ImportSource` requires `systemName` and means a source system, so a purely in-app capture session fits awkwardly. This sits with the catalogue item-import adapter, not with this guide.

⛔ **Do not mint a new `x-inherit-*` key for capture-time state.** An earlier draft of this guide proposed `x-inherit-capture` as the sanctioned home for it. That was withdrawn: draft and partial state is already covered by open vocabulary — `Completeness` at document level, plus `dataProvenance`, `provenance.humanVerdict`, `fieldProvenance` and `suggestedSubcategory` per asset — and the `x-inherit-*` namespace is separately slated for migration to a LinkML profile, so a new key would be debt with a due date on it. Until the open questions above are settled, the combinations shown in this guide are the answer, and none of the three capture modes needs a core schema change to build.
